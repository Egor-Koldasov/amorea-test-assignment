# Аналитика портфеля вилл

Прототип для анализа бронирований, комиссий, расходов и поступлений по виллам.

Работающее локальное приложение на Next.js и TypeScript с хранением в SQLite. На одной странице: фильтры, финансовые показатели, таблица по виллам и журнал качества данных.

## 1. Запуск

Нужны Node.js 22+ и npm. Все действия выполняются из корня проекта.

```bash
npm ci
npm run setup
npm run dev
```

Открыть http://127.0.0.1:3000. Приложение слушает только локальный адрес. Секреты, внешние сервисы и токены не нужны.

Проверки и production-запуск:

```bash
npm test
npm run typecheck
npm run build
npm start
```

`npm run setup` применяет миграции Drizzle и импортирует пять файлов из `Technical_Challenge_Data`. SQLite создаётся в `data/ledger.sqlite`. Путь можно переопределить переменной `DATABASE_PATH` для импорта и запуска. База и зависимости не включаются в Git.

Другой полный набор CSV импортируется так:

```bash
npm run setup -- /absolute/path/to/csv-directory
```

Каталог должен содержать все пять файлов с исходными именами и обязательными столбцами. Это **полный снимок**, не набор изменений: отсутствующие в новом снимке записи перестают участвовать в текущем отчёте. Старый снимок сохраняется.

| `src/lib/schema.ts`, `drizzle/` | Схема SQLite и миграции                                                |

| `src/lib/report.ts`             | Чтение активного снимка из базы                                        |
| `src/app/page.tsx`              | Серверный дашборд: фильтры, показатели, таблицы, исходные записи       |
| `src/app/api/issues/route.ts`   | Выгрузка журнала качества в CSV                                        |

Стек: Next.js App Router, TypeScript, Drizzle, SQLite, decimal.js, Vitest. Next объединяет интерфейс и серверную часть. SQLite не требует отдельного сервера. Расчёты изолированы от UI; денежные значения хранятся строками и считаются через Decimal.

Браузер не читает исходные CSV и не обращается к SQLite. Данные загружаются и проверяются при импорте; расчёт выполняется на сервере из сохранённого снимка. Для малого набора сервер читает снимок в память на каждый запрос. При росте объёма нужны индексы, SQL-агрегации и таблица дневных начислений.

Схема будущей системы, аудит и права доступа описаны в [ARCHITECTURE.md](ARCHITECTURE.md).

## 3. Правила расчёта

| Показатель                       | Правило                                                                                                                                                                                                   |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Начисления за проживание         | Распределяем стоимость равномерно по ночам. День выезда не включаем. Цен отдельных ночей нет — это наше допущение.                                                                                        |
| Поступления                      | Показываем отдельно, по `payment_date`. Поступление не равно выручке за тот же период.                                                                                                                    |
| Расходы                          | Учитываем `paid` и `pending` по `expense_date`. Предполагаем, что расход уже возник.                                                                                                                      |
| Неоплаченные расходы             | Отдельно показываем суммы со статусом `pending`.                                                                                                                                                          |
| Комиссия управляющей компании    | `gross_booking_value × ставка`. Ставку выбираем по объекту и дате заезда. Комиссию распределяем по ночам. OTA-комиссию из базы не вычитаем.                                                               |
| Полная отмена с полным возвратом | Начисления за проживание и комиссия управляющей компании — 0. Это допущение до подтверждения договора.                                                                                                    |
| OTA-комиссия при отмене          | Показываем отдельно как спорную сумму: неизвестно, удержали её или вернули. В основной оценочный результат не включаем и явно указываем это ограничение.                                                  |
| Результат собственника           | Начисления за проживание минус OTA-комиссии, комиссии управляющей компании и расходы. Это оценочный результат по включённым записям, а не остаток к выплате. Спорные OTA-комиссии по отменам не включены. |

### Формулы показателей

Все суммы — в IDR, для выбранного объекта и периода. Дубли, устаревшие версии и записи с критическими ошибками не входят в основные расчёты.

**1. Делим стоимость бронирования по ночам**

```text
Количество ночей = дата выезда − дата заезда
Сумма за период ≈ полная сумма ÷ количество ночей × ночи в выбранном периоде
```

Ночь даты выезда не учитываем. Так распределяем стоимость проживания, OTA-комиссию и комиссию УК. Чтобы не потерять деньги при округлении, остаток раздаём первым ночам по 1 IDR: например, 100 IDR за три ночи — это 34 + 33 + 33.

**2. Считаем показатели дашборда**

| Показатель | Как считаем |
| --- | --- |
| Начисления за проживание | Складываем стоимость всех включённых ночей за выбранный период. |
| OTA-комиссии | Складываем доли OTA-комиссий за те же ночи. Полную комиссию берём из CSV, а не рассчитываем по проценту. |
| Комиссия УК | Сначала для каждой брони: **полная стоимость × ставка УК**. Затем распределяем комиссию по ночам и складываем доли за период. |
| Расходы | Складываем расходы с датой внутри периода, как оплаченные (`paid`), так и ожидающие оплаты (`pending`). |
| Неоплаченные расходы | Складываем только расходы `pending` с датой внутри периода. Они уже включены в общие расходы — повторно их не вычитаем. |
| Поступления | Складываем уникальные корректные платежи `received` по **дате оплаты** внутри периода. Показываем отдельно от начислений. |

Ставку УК выбираем по объекту и дате заезда; обе границы срока действия ставки включены. Если подходящей ставки нет или их несколько, бронь отправляется на проверку. Полную комиссию округляем до целого IDR: половину — вверх. OTA-комиссию из базы расчёта УК не вычитаем.

```text
Результат собственника = начисления за проживание
                        − OTA-комиссии
                        − комиссия УК
                        − расходы
```

Это результат за период. Для остатка к выплате нужны ещё начальный остаток и уже сделанные выплаты собственнику — этих данных нет.

**3. Пример расчёта за сентябрь**

Бронь с **28 сентября по 3 октября**: всего 5 ночей, из них 3 в сентябре и 2 в октябре. Стоимость — 100 000 IDR, OTA-комиссия — 15 000 IDR, ставка УК — 17%. В сентябре также возник расход на 10 000 IDR.

| Показатель за сентябрь | Расчёт | Сумма, IDR |
| --- | --- | ---: |
| Начисления за проживание | 100 000 ÷ 5 × 3 | 60 000 |
| OTA-комиссия | 15 000 ÷ 5 × 3 | 9 000 |
| Комиссия УК | 100 000 × 17% ÷ 5 × 3 | 10 200 |
| Расходы | Расход с сентябрьской датой, даже если ещё не оплачен | 10 000 |
| **Результат собственника** | **60 000 − 9 000 − 10 200 − 10 000** | **30 800** |

Если гость оплатил все 100 000 IDR в сентябре, **поступления за сентябрь — 100 000 IDR**, хотя начисления — 60 000 IDR. Оставшиеся 40 000 IDR начислений относятся к октябрю. Поступления не прибавляем к результату собственника: иначе одна и та же бронь будет учтена дважды.

**4. Отмены и исключённые суммы**

- При полной отмене с полным возвратом начисления и комиссия УК равны **0**. Возврат повторно не вычитаем. Частичные возвраты и возвраты больше стоимости отправляем на проверку.
- **Спорные OTA-комиссии** = сумма OTA-комиссий по корректным отменённым броням с плановой датой заезда внутри периода. Показываем отдельно, из результата собственника не вычитаем: неизвестно, удержаны они или возвращены.
- **Исключённая стоимость проживания** = стоимость ночей за период из исключённых строк в IDR. Берём только строки с корректными датами и неотрицательной стоимостью, без дублей и устаревших версий. Это справочная сумма, а не подтверждённая потеря выручки.

Денежные возвраты по периодам не считаем: нет дат и подтверждений операций возврата. Даты оплаты расходов тоже отсутствуют, поэтому полноценный денежный поток рассчитать нельзя.

## 4. Ошибки и их обработка

Исходные CSV сохраняем без изменений. Причины исключений и предупреждений показываем в отчёте.

| Проблема                                        | Решение                                                                                                                                                    |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Полные дубли `R0015` и `P0075`                  | Учитываем один экземпляр, повтор исключаем.                                                                                                                |
| Неизвестные объекты в `R0034`, `P0017`, `E0017` | Исключаем из расчётов по объектам до исправления связи.                                                                                                    |
| Валюта USD в `R0061`                            | Исключаем из итога IDR: курса нет.                                                                                                                         |
| Возврат больше стоимости в `R0072`              | Исключаем из начислений до проверки.                                                                                                                       |
| Отрицательная OTA-комиссия в `R0102`            | Временно исключаем бронирование из расчётов начислений и комиссий целиком. Показываем исходную запись и причину. Не обнуляем комиссию и не меняем её знак. |
| Частичный возврат                               | Корректных примеров в наборе нет. Если появится, отправляем бронирование на проверку и исключаем из начислений и комиссий до определения правил.           |
| OTA-комиссия при канале `Direct`                | Сохраняем значение с предупреждением.                                                                                                                      |
| Пересекающиеся бронирования одной виллы         | Сохраняем записи с предупреждением.                                                                                                                        |

**Исключение:** запись не участвует в соответствующем расчёте. **Предупреждение:** участвует, но требует проверки.

### Пересечения

После удаления полного дубля среди неотменённых бронирований найдены **73 пары пересечений: 87 бронирований на 17 виллах**. Эта проверка выполнена до остальных исключений из расчётов. Одно бронирование может входить в несколько пар.

Считаем виллу одной единицей размещения. Выезд и следующий заезд в один день не являются пересечением.

Причина пересечений неизвестна. Если виллы сдаются по отдельным помещениям, нужен идентификатор помещения — его нет. Если пересечения вызваны ошибочными бронированиями, итог может быть завышен. Автоматически выбирать «правильную» запись нельзя.

## 5. Ограничения данных

| Чего нет                                         | Последствие                                                                                                                            |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| Даты оплаты расходов                             | Нельзя распределить денежные выплаты по периодам. `paid` не говорит, когда заплатили. `expense_date` не используем вместо даты оплаты. |
| Дат и подтверждения денежных возвратов           | Нельзя распределить возвраты денег по периодам. `refund_amount` сам по себе не доказывает движение денег.                              |
| Начального остатка и истории выплат собственнику | Нельзя определить остаток к выплате собственнику.                                                                                      |
| Курсов валют                                     | Нельзя объединить разные валюты в один итог.                                                                                           |

Показываем зарегистрированные поступления. **Полный денежный поток восстановить нельзя.** Поступления минус начисленные расходы не называем денежным потоком.

## 6. Открытые решения

У всех 12 отменённых бронирований возврат равен полной стоимости, но OTA-комиссия положительная. Неизвестно, сохраняется ли она после отмены.

Для этих отмен приняли правила из раздела 3: нулевые начисления за проживание и нулевую комиссию управляющей компании; OTA-комиссию показываем отдельно как спорную.

Корректных частичных возвратов в наборе нет. Единственный ненулевой возврат у неотменённого бронирования — `R0072`, где возврат больше стоимости. Правило для будущих частичных возвратов: проверка и временное исключение из начислений и комиссий. Для автоматической обработки нужны причина возврата, период корректировки и правила пересчёта комиссий.

Отрицательная OTA-комиссия `R0102` может быть корректировкой, но подтверждения нет. До проверки исключаем бронирование из начислений и комиссий целиком. Это уменьшает полноту результата, поэтому исключённую стоимость показываем отдельно. Исключение бронирования само по себе не отменяет зарегистрированные платежи: их проверяем отдельно.

Во всех 20 строках `commission_rules.csv` база комиссии — `gross_booking_value`.

### Округление

Денежные расчёты выполняем десятичной арифметикой. Комиссию за всё бронирование округляем до целого IDR по правилу HALF_UP. При распределении стоимости и комиссий по ночам целые IDR распределяем равномерно, остаток по одному IDR добавляем первым ночам. Сумма по ночам должна точно совпадать с суммой за бронирование.

## 8. Дополнительные правила

- `modified` считается текущим состоянием бронирования, а не автоматическим дублем.
- Полные дубли удаляются из расчёта. При разных версиях одного бронирования выбирается максимальный `updated_at`. Конфликт на одной дате или конфликт другого типа сущности исключается до проверки.
- `effective_from` и `effective_to` включительны. Для неотменённого бронирования должна найтись ровно одна пригодная ставка на дату заезда. Иначе бронирование исключается из начислений и комиссий.
- Начало и конец фильтра включительны. Для проживания выбираются ночи, для расходов — `expense_date`, для поступлений — `payment_date`.
- Gross bookings означает стоимость неотменённого проживания до комиссий, распределённую по ночам; исключённые записи не учитываются. Это не объём новых продаж: дата создания бронирования отсутствует.
- Спорные OTA-комиссии по отменам отбираются по плановой дате заезда и не вычитаются из основного результата. Их сумма показывает возможное уменьшение оценки, но не доказывает расход или дату его возникновения.
- Отсутствующий объект, неизвестное бронирование, несовпадение объекта платежа и бронирования, чужая валюта или некорректная сумма исключают платёж. Корректный платёж по финансово исключённой брони остаётся с предупреждением. Нулевые платежи остаются с предупреждением и не увеличивают поступления.
- Журнал качества фильтруется по объекту и соответствующей дате записи. Замечания по справочникам и записи с некорректными датами не имеют надёжной даты для отбора и показываются независимо от периода.
- Одна запись может иметь несколько замечаний. Пересечение показывается с обеих сторон: 73 пары дают 146 замечаний. Число замечаний не равно числу ошибочных строк.
- Исключённая стоимость показывается по ночам, только в IDR, без полных дублей и устаревших версий. Это стоимость исходных исключённых записей, а не доказанная потеря выручки. Суммы в USD можно увидеть в деталях исходной записи.

## 10. Ограничения и следующие шаги

Прототип рассчитан на локальный запуск с небольшими синтетическими данными. Авторизации, банковской сверки, загрузки файлов через браузер и редактирования записей нет. Снимки хранят историю источников, но отдельный интерфейс сравнения версий не реализован. Содержимое сущностей хранится как JSON с индексируемыми служебными полями; для production нужны отдельные типизированные таблицы и ограничения базы.

Три следующих шага:

1. Согласовать с финансовым директором признание доходов, возвраты, комиссии и остатки; получить реальные схемы платежей и расчётов с собственниками.
2. Подключить регулярную загрузку, нормализованное хранение, очередь проверки ошибок и сверку с банком/OTA.
3. Добавить аутентификацию, права по объектам, резервное копирование и мониторинг; проверить пилотный месяц вместе с финансами.
